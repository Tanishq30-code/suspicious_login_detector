5How the detection logic works

[m [31m-

Each application source is parsed by a small dedicated matcher and normalized to a common[m [31m- epoch|ip|user|app event, so the rest of the pipeline never needs to know which log format an[m [31m- event came from:

[m [31m- [m [31m- [m [31m- [m [31m- [m [31m- [m [31m- [m [31m-
TypeMatches onExample
sshFailed password / PAM authentication failuresshd[…]: Failed password for root from 203.0.113.45 …
webLOGIN_FAILED with ip=/user= tokensapp[login]: LOGIN_FAILED ip=203.0.113.45 user=admin …
dbAccess denied for user '…'@'…'mysqld: Access denied for user 'root'@'198.51.100.77' …
apiJSON lines with "event":"auth_failure"{"event":"auth_failure","ip":"…","user":"…"}
[m [31m-

For each distinct IP across all sources combined, its failed-attempt timestamps are sorted and[m [31m- the script slides a window across them: if any (threshold + 1) consecutive attempts fall[m [31m- within window seconds of each other, the IP is flagged. This distinguishes a genuine burst from[m [31m- the same attempt count spread thinly over hours, which keeps false positives low — the bundled[m [31m- clean_traffic.log benchmark scenario exists specifically to prove that.

[m [31m-

Flagged IPs get a severity: MEDIUM at baseline,[m [31m- HIGH if attempts reach 2× the threshold or the IP hit 2+[m [31m- applications, and CRITICAL if it hit 3 or more distinct applications —[m [31m- reflecting that the same source attacking multiple systems is materially more dangerous than one noisy[m [31m- brute-forcer on a single service.

[m [31m-[m [31m-

6Response workflow: block → recover

[m [31m-

Detection, blocking, and recovery are deliberately separate steps so nothing destructive ever happens[m [31m- automatically:

[m [31m-
    [m [31m-
  1. Detect — a normal run (optionally -B) identifies and reports flagged IPs; each gets a Recovery Actions checklist in the text report regardless of -B.
    2. [m [31m-
  2. Block (opt-in, reviewable) — -B writes block_commands_*.sh and a blocklist.tsv row (ip, first-blocked time, expiry, severity, active). Nothing is applied to the firewall unless you also pass -x as root.
    3. [m [31m-
  3. Recover — run -r periodically (e.g. daily via cron). Entries past the -c cooldown get an unblock_commands_*.sh script and flip to recovered; entries still cooling down are reported with hours remaining and left active.
    4. [m [31m-
[m [31m-[m [31m-

7Benchmarking / proof of accuracy

[m [31m-

-b exists to answer "how do we know this actually works?" with evidence rather than a[m [31m- single demo run. It executes the full pipeline against three scenarios with known, hand-verified ground[m [31m- truth (sample_logs/*.expected / expected_combined.txt) and reports a hard[m [31m- PASS/FAIL per scenario:

[m [31m- [m [31m- [m [31m- [m [31m- [m [31m- [m [31m-
ScenarioWhat it proves
combined-defaultCross-application correlation is correct — the multi-app attacker is found and escalated, the single-app attacker is found at the right severity, and quiet IPs stay unflagged.
ssh-onlyThe core sliding-window algorithm alone: a real burst is caught, a slow drip of the same total attempts over an hour is correctly ignored.
clean-trafficZero false positives on entirely benign traffic (successful logins, cron, no failures at all).
[m [31m-

The report also records elapsed time and throughput (lines/sec) per scenario, so it doubles as a[m [31m- lightweight performance benchmark alongside the accuracy proof.

9Known limitations & extension ideas

[m [31m-
    [m [31m-
  • IPv4 only — IPv6 source addresses are skipped by the validation regex.
    • [m [31m-
  • Timestamps assumed UTC — ISO-8601 timezone offsets (e.g. +05:30) are[m [31m- currently ignored during parsing so events from different sources line up on one timeline; real[m [31m- deployments spanning timezones should normalize logs to UTC before feeding them in.
    • [m [31m-
  • Four built-in application parsers — adding a fifth log format means adding one more[m [31m- matcher block to normalize.awk; the rest of the pipeline (detection, severity, blocking,[m [31m- recovery, benchmarking) is format-agnostic.
    • [m [31m-
  • Blocking is IP-only — it does not attempt to identify or lock the targeted user[m [31m- accounts; that's intentionally left as a manual step in the Recovery Actions checklist.
    • [m [31m-
  • Alerting — currently email only; the CSV output is intentionally machine-parsable so[m [31m- it can be piped into Slack/webhook alerting later without touching the core logic.
    • [m [31m-

10Troubleshooting

[m [31m- [m [31m- [m [31m- [m [31m- [m [31m- [m [31m- [m [31m- [m [31m- [m [31m- [m [31m-
SymptomLikely cause / fix
Permission denied running the scriptRun chmod +x suspicious_login_detector.sh once.
cannot read log fileThe path in -a TYPE:FILE/-f is wrong, or you need sudo to read system logs.
unknown source typeTYPE in -a TYPE:FILE must be exactly ssh, web, db, or api.
-x requires -BPass both together: -B -x. -x alone has nothing to execute.
Block commands weren't actually appliedBy design — without -x (and root), -B only writes the reviewable script. Run it yourself, or add -x.
this script requires GNU awkInstall gawk, e.g. sudo apt install gawk (Debian/Ubuntu) or sudo yum install gawk (RHEL/CentOS).
Everything shows as unflagged unexpectedlyLower -t or widen -w — remember the rule is more than N attempts, so -t 5 needs 6+ attempts.
