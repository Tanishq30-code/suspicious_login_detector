Suspicious Login Detector v2.0

A dependency-free bash/awk tool that correlates failed logins across multiple application types (SSH, web app, database, API gateway), flags brute-force patterns, generates firewall block commands, walks flagged IPs through a recovery workflow, and proves its own accuracy with a bundled benchmark suite.

1What's new in v2.0

v1.0 scanned a single SSH auth log. v2.0 adds four capabilities, each addressing a specific piece of reviewer feedback on the original design:

🎯 Benchmark / proof mode

-b re-runs the detector against three bundled, ground-truth-tagged scenarios and prints a detected-vs-expected pass/fail table — objective proof of detection accuracy, not just a demo run.

🧩 Multi-application log sources

The tool now parses four independent application log formats — SSH, a web app, a database, and an API gateway — and correlates the same attacking IP across all of them.

🚫 Block that IP

-B generates ready-to-review iptables/ufw block commands for every flagged IP and records them in a persistent blocklist.

♻️ Recovery actions

Every flagged IP gets a recovery checklist in the report, and -r reviews the blocklist after a cooldown period and generates the matching unblock commands.

Requirements

  • Any Linux distribution with bash
  • gawk (GNU awk) — used for mktime()/strftime()/match()
  • Standard coreutils: date, mkdir, mktemp
  • Optional: mailx/sendmail for email alerts, iptables/ufw to actually apply generated blocks
All files for this project live entirely under ~/Downloads/personal/suspicious-login-detector/ on this machine. Nothing here connects to, reuses, or depends on any other project or client work — it is self-contained and reads only the log paths you explicitly give it (or the bundled demo logs).
Block commands are never auto-executed. -B only writes a reviewable block_commands_*.sh script and a blocklist entry. The actual iptables/ufw command only runs if you additionally pass -x and the script is running as root — review the generated script first, every time.

2Step-by-step: run the demo

Open a terminal in the project folder

cd ~/Downloads/personal/suspicious-login-detector

Make the script executable (first time only)

chmod +x suspicious_login_detector.sh

Run it with zero flags — the four bundled application sources

./suspicious_login_detector.sh

With no -a/-f given, it automatically loads all four demo sources (ssh, web, db, api) and correlates them by IP.

Read the summary

The same attacker IP (203.0.113.45) is seen hitting SSH, the web app, and the API gateway — three different applications — so it's escalated to CRITICAL even though no single source alone would look that severe. A separate IP brute-forcing only the database is correctly flagged HIGH on attempt volume alone:

Flagged suspicious IPs   : 2
---------------------------------------------------------------------
IP               Attempts  AppsHit   Applications       Username(s)               Severity
198.51.100.77    11        1         db                 root                      HIGH
203.0.113.45     12        3         ssh;web;api        admin;root;test;oracle    CRITICAL
---------------------------------------------------------------------
Recovery Actions (per flagged IP):

  IP 203.0.113.45  (severity: CRITICAL)
    [ ] Block this IP at the perimeter firewall (run with -B to generate commands)
    [ ] Force logout / invalidate active sessions for: admin;root;test;oracle
    [ ] Require a password reset for the targeted account(s) above
    [ ] Review recent SUCCESSFUL logins from 203.0.113.45 for signs of prior compromise
    [ ] Keep the block in place for 24h, then re-review with -r (recovery mode)

Generate block commands for the flagged IPs

./suspicious_login_detector.sh -B

Writes reports/block_commands_<timestamp>.sh (commented iptables + ufw commands, one per flagged IP) and adds each IP to blocklist.tsv with status active. Review the script, then run it yourself when ready.

Later: review the blocklist and unblock what's past cooldown

./suspicious_login_detector.sh -r -c 24

Checks every active entry in blocklist.tsv; anything blocked more than 24h ago gets an unblock command in reports/unblock_commands_<timestamp>.sh plus a recovery checklist (confirm no further attempts, rotate credentials, keep monitoring), and its status flips to recovered. Anything still inside the cooldown is left active.

Prove it works: run the benchmark suite

./suspicious_login_detector.sh -b

Runs three controlled scenarios — the combined multi-app demo, SSH in isolation, and a clean-traffic-only log — against bundled ground truth, and writes reports/benchmark_<timestamp>.txt showing PASS/FAIL per scenario plus timing. This is the accuracy "proof" referenced in the project write-up.

5How the detection logic works

Each application source is parsed by a small dedicated matcher and normalized to a common epoch|ip|user|app event, so the rest of the pipeline never needs to know which log format an event came from:

TypeMatches onExample
sshFailed password / PAM authentication failuresshd[…]: Failed password for root from 203.0.113.45 …
webLOGIN_FAILED with ip=/user= tokensapp[login]: LOGIN_FAILED ip=203.0.113.45 user=admin …
dbAccess denied for user '…'@'…'mysqld: Access denied for user 'root'@'198.51.100.77' …
apiJSON lines with "event":"auth_failure"{"event":"auth_failure","ip":"…","user":"…"}

For each distinct IP across all sources combined, its failed-attempt timestamps are sorted and the script slides a window across them: if any (threshold + 1) consecutive attempts fall within window seconds of each other, the IP is flagged. This distinguishes a genuine burst from the same attempt count spread thinly over hours, which keeps false positives low — the bundled clean_traffic.log benchmark scenario exists specifically to prove that.

Flagged IPs get a severity: MEDIUM at baseline, HIGH if attempts reach 2× the threshold or the IP hit 2+ applications, and CRITICAL if it hit 3 or more distinct applications — reflecting that the same source attacking multiple systems is materially more dangerous than one noisy brute-forcer on a single service.

6Response workflow: block → recover

Detection, blocking, and recovery are deliberately separate steps so nothing destructive ever happens automatically:

  1. Detect — a normal run (optionally -B) identifies and reports flagged IPs; each gets a Recovery Actions checklist in the text report regardless of -B.
  2. Block (opt-in, reviewable) — -B writes block_commands_*.sh and a blocklist.tsv row (ip, first-blocked time, expiry, severity, active). Nothing is applied to the firewall unless you also pass -x as root.
  3. Recover — run -r periodically (e.g. daily via cron). Entries past the -c cooldown get an unblock_commands_*.sh script and flip to recovered; entries still cooling down are reported with hours remaining and left active.

7Benchmarking / proof of accuracy

-b exists to answer "how do we know this actually works?" with evidence rather than a single demo run. It executes the full pipeline against three scenarios with known, hand-verified ground truth (sample_logs/*.expected / expected_combined.txt) and reports a hard PASS/FAIL per scenario:

ScenarioWhat it proves
combined-defaultCross-application correlation is correct — the multi-app attacker is found and escalated, the single-app attacker is found at the right severity, and quiet IPs stay unflagged.
ssh-onlyThe core sliding-window algorithm alone: a real burst is caught, a slow drip of the same total attempts over an hour is correctly ignored.
clean-trafficZero false positives on entirely benign traffic (successful logins, cron, no failures at all).

The report also records elapsed time and throughput (lines/sec) per scenario, so it doubles as a lightweight performance benchmark alongside the accuracy proof.

8Automating it with cron

# crontab -e

# Every 15 minutes: detect + generate block commands, email only when flagged
*/15 * * * * /home/<you>/Downloads/personal/suspicious-login-detector/suspicious_login_detector.sh \
  -B -q -m you@example.com \
  -o /home/<you>/Downloads/personal/suspicious-login-detector/reports

# Once a day: review the blocklist and lift anything past a 24h cooldown
0 3 * * * /home/<you>/Downloads/personal/suspicious-login-detector/suspicious_login_detector.sh -r -c 24 -q
Reading real system logs (/var/log/auth.log, database/webserver logs) and applying -x block commands usually requires root. When scheduling via root's crontab, use absolute paths exactly as shown above, since cron jobs run with a minimal environment.

9Known limitations & extension ideas

  • IPv4 only — IPv6 source addresses are skipped by the validation regex.
  • Timestamps assumed UTC — ISO-8601 timezone offsets (e.g. +05:30) are currently ignored during parsing so events from different sources line up on one timeline; real deployments spanning timezones should normalize logs to UTC before feeding them in.
  • Four built-in application parsers — adding a fifth log format means adding one more matcher block to normalize.awk; the rest of the pipeline (detection, severity, blocking, recovery, benchmarking) is format-agnostic.
  • Blocking is IP-only — it does not attempt to identify or lock the targeted user accounts; that's intentionally left as a manual step in the Recovery Actions checklist.
  • Alerting — currently email only; the CSV output is intentionally machine-parsable so it can be piped into Slack/webhook alerting later without touching the core logic.
